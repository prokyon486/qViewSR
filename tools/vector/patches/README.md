# VTracerの大画像対応とCPU処理の修正

`vtracer-0.6.15-qviewsr.patch` は、公式Python package 0.6.15と、その固定依存visioncortex 0.8.10へ適用します。対象ソース、Rustツールチェーン、パッチのSHA-256は `../dependencies.json` に記録しています。

## 色の合計値

上流 `visioncortex/src/color.rs` の `ColorSum` はRGBA各成分の合計と画素数を `u32` で保持します。`add` と `merge` の加算が上限を超えると、通常のreleaseビルドでは値が折り返します。255の合計では16,843,010画素から発生し、後続の平均色や領域間色差を誤らせます。

合計と画素数を `u64` へ変更しました。平均値の整数除算と最終的な8bit色への変換は変更していません。各clusterは合計を2個持つため、必要メモリーが増えます。workerの事前見積もりも190 bytes/pxへ増やしています。

パッチに含むRustテストは画像を確保せず、集計値の結合だけで検証します。

- 白い33,554,432画素相当を結合し、RGBとalphaが255を維持すること。
- 大きな白・黒領域の結合で、重み付き平均が170になること。追加画素とclear後の再利用も確認すること。
- 画素数が2^32になってもcounterと平均を維持すること。このテストは集計型の検証であり、バックエンド全体が2^32画素画像を処理できるという意味ではありません。

同じテストを元の32bit実装へ追加したreleaseビルドでは3件とも失敗し、修正版では3件とも成功しました。

## 境界計算の省略

`color_clusters/runner.rs` のdeepen条件を、色差判定→`patch_good` の順へ変更しました。`BuilderImpl::stage_2` は近傍が空の場合にcontinueするため、渡される近傍配列は必ず非空です。両条件は読み取りのみで、`patch_good` は領域を一時的なBinaryImageへ展開して境界を走査します。色差で棄却される領域では、この生成と走査を省けます。近似条件や出力品質のパラメーターは変更していません。巨大画像での速度改善量は画像に依存します。

## 細い領域の判定を短絡

`patch_good` が必要とする条件は「境界画素数 < 領域の全画素数」です。上流の境界画素は、上下左右の少なくとも一つが背景または画像外となる可視前景画素で、辺の長さや8近傍の判定ではありません。従来は毎回、外接矩形の二値画像と全境界画素の配列を作っていました。

activeな非ZERO領域では、holesが空なら「上下左右がすべて同じ領域となる画素が一つ以上ある」と同値です。indicesを走査し、最初の内部画素でtrueを返します。holesがある場合は、通常の統合経路でholesがindicesへ既に追加された画素の部分集合であるため、可視画素数自体が全画素数より少なく、条件はtrueになります。

ZEROには、indicesに含まれない捨てた透過key画素も同じownerとして残り得ます。またdeepen後の複製は現在の画素所有者ではありません。そのためZERO、非active領域、別途コピーしたClusterでは先に従来の二値画像による計算へ戻します。active確認にはowner、merged_into、Builder内の実体との参照一致を使います。公開のperimeter API、面積の上下限、min_area==0の扱いは変更しません。

Rust回帰テストは各predicate呼出しを旧計算と比較し、特殊な領域と既存の領域統合差分テストを合わせて検証します。既存140画像に2048×2048の疎な外接矩形・細い輪郭・入れ子の穴と色・Discardされたkeyの近似色を加えた145画像で、SVGがbyte一致しました。単発計測では入れ子色画像の領域確定が0.493秒から0.365秒、全体が0.946秒から0.814秒でした。これは当該fixtureの結果であり、巨大な実画像の改善率を示す数値ではありません。

## 面積別の候補索引

`color_clusters/builder.rs` の `stage_2` は面積を昇順に処理し、そのたびに全clusterを走査していました。面積→候補indexの表を作り、該当候補だけを元と同じindex昇順で処理します。既存の面積/countの意味と処理順、統合先の選び方、deepen/hollow処理は維持します。

- 非空のZERO（index 0）も初期候補に含めます。
- 統合先の新面積は元の正の面積＋現在面積であり、現在より必ず大きくなります。新面積へ候補を追加し、古い候補は現在面積の照合で除外します。
- deepenした元領域の複製を再登録しません。その面積は処理済みで、元の全走査と同様に再訪しません。
- 候補のindex順ソートと重複除去で、元の一回ずつの走査順を保ちます。

Rust回帰テストには旧走査を `cfg(test)` の参照実装として残しています。768条件・29,394段階で全領域の画素列・色合計・穴・統合先・出力順・面積/count・反復位置を比較し、一致しました。stale候補、deepenされた複製、非空ZEROも実際に通ることを検証します。この索引はVTracerの通常の `Runner::run` / `Builder::start` 経路を対象とします。外部コードが準備後に公開mutable accessorを使って領域を任意変更する使い方は索引更新の対象外です。VTracerはその呼び方をしません。

## 面積を管理する木構造

巨大画像の実行中スタックを3回採取すると、いずれも新しい面積をソート済み `Vec<Area>` へ挿入する `memmove` にいました。1回の計測では配列長3,340,750、挿入位置1,355,136、要素16byteで、1挿入につき31,769,824byte（約30.3MiB）を移動していました。候補索引だけではこの配列移動は残ります。

面積→countを標準ライブラリの `BTreeMap` へ置き換え、新規面積の挿入時に配列全体を移動しないようにしました。処理済みのキー/countも残し、現在面積より大きい次のキーへカーソルを進めます。統合後の面積は必ず現在面積より大きくなるため、過去へ新規キーが挿入されることはありません。過去の面積を持つ統合先のcount減算、countが0の要素の処理、反復数、最後の背景領域判定も維持します。

Rust差分テストは旧Vec実装を参照として残し、木構造の全キー/count・次のカーソル・全領域状態を768条件・29,394段階で比較します。細線判定も含め、単一スレッドで実行した回帰テストでは86,853回の旧predicateとの比較が一致しました。145画像のSVGもbyte一致しています。小中画像では配列が小さいため、速度は概ね同等です。巨大画像の実測結果は別途記録し、未完了の旧版を完了時間として扱いません。

## 曲線生成の並列化と書き出し

色領域確定後、各clusterから曲線を作る工程は領域本体を変更しません。Rust標準ライブラリのscoped threadを使い、最大16workerへ独立領域を配り、完成した結果を元の描画位置へ収集します。新しいcrate依存は追加していません。領域統合自体は直列のままです。

ファイル変換のPython bindingは `num_threads=None|1..16` を受け付けます。自動の場合は利用可能CPU数を上限16で使用し、小画像（262,144画素未満）は直列にします。明示予算もCPU数と領域数で制限します。0や17以上はValueErrorです。予算は呼出しごとのConfigへ保持し、共有環境変数による競合を避けます。

同bindingの純Rust変換を `py.allow_threads` で囲み、GILを解放します。未修正版で変換中のPython tickが0回だった対照に対し、修正版では10msごとのtickが動くことを確認しました。raw/pixel bindingのGIL動作は変更していません。64KiBの `BufWriter` は同じSVG文字列を書き出し、書込み・明示flushの失敗をPython例外へ伝播します。

隔離比較では乱数32種×4条件、二値透明、既存イラスト、ノイズ・勾配を含む140画像のSVGが索引前後および並列前後でbyte一致しました。1/8/16workerの比較を含む152回と、buffered outputの代表24回も一致しました。1024pxノイズの曲線工程は1worker約0.93秒→16worker約0.09秒、全体は約3.85秒→3.03秒でした。バッファ出力後は全体約2.61秒です。いずれも同一PCの単発測定で、任意画像での倍率を保証する数値ではありません。並列化の一時メモリー増加は、この1024px入力では約31～36MiBでした。

## 巨大画像の塗り変換の実測

17984×21120（約3.8億画素）の準備済みPNGを、同じ品質設定・16スレッド指定で変換しました。VTracerの塗り変換は90.73秒で正常終了し、読込9.79秒、領域確定55.92秒、454,826領域の曲線生成16.08秒、SVG書出し7.42秒でした。最大RSSは18.57GiB、swapは0です。この時間には元画像の準備、元線弱化、主線トレースを含みません。

候補索引だけを適用した比較版は35分29秒時点でも未完了でした。この時間を旧版の完了時間として扱いません。新しいSVGは約165.51MiBで、元データを省略せず保存しました。数値は検証PC・当該画像の単発結果であり、GUIの読込・描画時間とは別です。

## 固定依存と識別

PyPIのソースアーカイブに含まれるCargo.lockには、ソース本体に含まれないwebappの依存も残っていました。パッチでは不要な13パッケージを除き、残る依存のバージョンとchecksumを維持しています。visioncortexだけをSHA照合済みのローカル修正ソースへ差し替えます。ビルドは `--locked` で行い、依存の自動更新を許可しません。

Pythonのdistribution versionは `0.6.15+qviewsr.4`、モジュールの `vtracer.__qviewsr_patch__` は `large-color-sums-area-tree-parallel-sparse-v4` です。元のRust側VTracer versionは0.6.12のままなので、SVG内の上流生成コメントは変わりません。workerの塗りキャッシュにはPython distribution versionが入り、旧版の塗りSVGだけが無効になります。元画像と元線弱化のキャッシュ識別は変更しません。

## 再ビルドと検証

リポジトリルートで実行します。

```sh
python3 tools/vector/setup_vector.py
python3 tools/vector/setup_vector.py --check
.local/vector-probe-venv/bin/python tools/vector/test_vtracer_patch.py
```

セットアップは、公式Rust 1.90.0のrustc/std/cargoを固定SHAで `.local/vector-patched-vtracer/rust` へ導入し、maturin 1.9.4でwheelを生成します。Python 3.12では、上流が使用するPyO3 0.19.2に `PYO3_USE_ABI3_FORWARD_COMPATIBILITY=1` を設定します。Rustテストはビルド前、Pythonの実変換テストはwheel導入後に実行します。

初回成功後のオフライン再ビルド:

```sh
python3 tools/vector/setup_vector.py --offline --rebuild-vtracer
```

`vtracer-small-image-baseline.json` は、修正前の公式0.6.15 wheelで白・図形・小さな色差の勾配・細かな領域・ノイズ・二値透過の6画像を2回ずつ処理し、再現性を確認して記録したSVGのSHA-256です。元wheelの拡張モジュールSHA、画像の画素SHA、処理パラメーターも記録しています。セットアップ後の検証では、自動／1／8／16スレッドで6画像すべてのSVGがバイト一致することを確認します。baselineを取り直す `--record-baseline` は未修正0.6.15でのみ使用できます。

実行済みのRust回帰テスト結果は `.local/vector-patched-vtracer/regression`、オフライン再ビルドの記録は同ディレクトリ直下の `offline-rebuild.log` に保存しています。ビルドの正式な再現記録は `qviewsr-build.json` です。ログやバイナリをGitへ追加しません。
